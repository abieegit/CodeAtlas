# 07 — Software Engineering Review (prompt §10)

Two parts: **(1)** the design evaluated against the requested principles, honestly —
including where a principle is *not* satisfied; **(2)** numbered findings **E1–E17** that
the diagrams and the build must account for. No code was changed and nothing here should be
read as an approved refactor — these are reported issues with recommended handling.

---

## Part 1 — Principle-by-principle evaluation

| Principle | Verdict | Reasoning from source |
| --- | --- | --- |
| **Separation of concerns** | ✅ genuinely met | HTTP (routes/controllers) vs pipeline (services/parser) vs persistence (`graph.service`) vs AI (`services/analysis/*`) vs presentation (frontend) are separate directories with one-way imports. A reviewer can open any one file and understand its job |
| **Single Responsibility** | 🟡 mostly met, two real violations | Pipeline modules are individually cohesive (`ast.parser` parses, `entity.extractor` extracts). Violations: `repository.controller.ts:51-134` mixes validation, orchestration, response shaping (`categoryCounts`, 104-111) and cleanup policy (126-133); `graph.service.ts` mixes persistence, querying, provenance reconstruction and connectivity health in one 367-line module |
| **Open/Closed** | 🟡 met for analysis, blocked for the meeting requirements | Adding a node type requires editing the `EntityType` union **and** `ENTITY_LABELS` (`graph.service.ts:19-27`) — two places, though the allow-list is the right defensive pattern. Blocking: `chatComplete(messages, options)` (`llm.client.ts:38-44`) takes **no** credential argument, so per-user keys (UR-08) cannot be added without editing this module rather than extending it (E8) |
| **Liskov** | ✅ not applicable in a harmful way | There is one class hierarchy in the pipeline (`LlmError extends Error`) and it is used consistently by controllers catching `LlmError` and reading `.status` |
| **Interface Segregation** | ✅ met by accident of style | The types are data contracts (`GraphNode`, `GraphRelationship`, `GraphData`, `AnalysisReport`), not fat behavioural interfaces. ⚠️ Do **not** fix the missing abstraction by inventing one giant `AnalysisService` interface later |
| **Dependency Inversion** | 🟡 weakest point, and the fix is narrow | Everything imports concrete modules directly. Inside one language and one process at this scale that is acceptable and keeps the code readable. It becomes a real problem exactly where the meeting requirements introduce variability: **the LLM provider (per-user credentials, provider swap), the storage location (disk vs object), and the payment boundary.** Recommendation: introduce interfaces **only** at those three seams (E8, D-09, D-08) and leave the rest as direct imports |
| **High cohesion / low coupling** | ✅ high cohesion; coupling is a wide fan-in, not a cycle | `analysis.service` pulls in six modules but each call is a distinct pipeline phase. No circular import was found between the parser modules and the services |
| **Circular dependencies** | ✅ none found | Direction is consistently `routes → controllers → services → parser/utils → config/database`. ⚠️ Risk to avoid when the target lands: `parser.service` already imports the AI cache invalidators (`parser.service.ts` → `analysis/report.service`) — once usage metering and entitlements also live in `services/analysis/`, an invalidation→metering→entitlement chain can easily close a cycle. Put the invalidation seam behind a small events/registry module instead of importing services into services |
| **Appropriate data ownership** | ❌ not satisfied today | The only durable store is Neo4j, and it holds graph structure **plus** the identity notion (`repository` property) **plus** source fragments (`sourceSnippet`). Identity, ownership, runs, usage, plans and entitlements have no owner at all. `listRepositories()` (`graph.service.ts:337-345`) is an ownership registry implemented as a `DISTINCT r.name` query — that is the clearest statement of the problem |
| **Authentication & authorization boundaries** | ❌ absent | No middleware, no principal, no role. Every endpoint including `POST /api/repositories/analyze` is public, and `cors()` is bare (`server.ts:31`). This is the largest gap between the current build and the meeting requirements, and it cannot be dressed up in a diagram |
| **Repository isolation** | ❌ absent, and **actively unsafe if multi-user** | `fetchGraph()` with no parameter returns every stored `:Entity` node (`graph.service.ts:151-152`); with a parameter it trusts the caller-supplied name; and re-analysis deletes all nodes of that name first (`63-69`). Two users naming different uploads the same thing corrupt each other (E1) |
| **Secure credential handling** | 🟡 good on the platform key, nothing else exists | Positive: `LLM_API_KEY` lives only in gitignored `backend/.env`, is read in exactly one place (`env.ts:35`), never reaches the client, and `Authorization` appears only in the outbound fetch (`llm.client.ts:69`). Negative: user passwords, sessions and BYOK keys do not exist yet, so there is no hashing, encryption, redaction or rotation machinery to review (D-01, UR-08) |
| **Data integrity & transactional consistency** | ❌ weak | Per-node and per-edge `session.run` calls with `CREATE`, no `MERGE`, no explicit transaction, no constraints/indexes. A failure mid-write leaves a **partially written graph** that the next `DETACH DELETE` will clean up, but that read path can and will observe a half-written repository (E5) |
| **Payment-event idempotency** | N/A — nothing exists | Flagged so nobody assumes it was evaluated. It only becomes a real concern if D-08 keeps payments in scope |
| **Error handling & recovery** | ✅ strong in the pipeline, 🟡 at the edges | Per-file try/catch, unresolved-edge omission, best-effort persistence, mapped LLM errors — all verified. Edges: the global handler returns `error.message` raw to the client (`server.ts:52-55`); Multer storage failures are not surfaced as a distinct client error; no timeout/retry policy on the Neo4j driver; no startup recovery for an interrupted run |
| **Testability & maintainability** | ✅ genuinely good | The app is exported and listens only when run directly (`server.ts:59-65`), which is why 23 test files can drive real HTTP behaviour without a port. Pure modules (`repo-digest`, `graphFilters`, `executionFlows`) are tested directly; the gated Neo4j round-trip skips instead of lying. Maintains well because file-per-responsibility |
| **Performance & scalability for an FYP** | ❌ the real risk is the write path, not the scale | 461 nodes + 1 148 edges ⇒ ~1 610 statements plus 2 296 unindexed `{id, repository}` lookups, all inside one HTTP request. The build log's own ~65 s figure for a **53-node** repository is consistent with that, not with repository size. Fixing batching + constraints is a bigger win than any infrastructure change (E5, D-04) |

## Part 2 — Design findings E1–E17

Severity: 🔴 blocks the target product · 🟠 must be fixed before multi-user exposure ·
🟡 quality/maintainability. "Owed to" = which requirement/diagram depends on it.

| ID | Sev | Finding | Evidence | Impact & recommended handling | Owed to |
| --- | --- | --- | --- | --- | --- |
| **E1** | 🔴 | **Repository identity is a sanitized filename, and it is also the delete key.** `sanitizeName()` derives the name from the uploaded archive's filename; `saveGraph` deletes all nodes with that `repository` value before re-creating them | `ingestion.service.ts:19-28,66,107-111`; `graph.service.ts:63-69` | Different users/projects with the same archive name overwrite or destroy each other's graphs. Ownership, quotas, history, admin scoping and safe caching are all impossible until identity is an application-minted UUID. **Handle first, before any §B/§C module is built** | D-03; UR-03/06/07/09; AR-02/03; Diagrams 2,5,7,8 |
| **E2** | 🔴 | **No authorization anywhere; unscoped graph reads.** Any caller can read any repository, and omitting the parameter returns *all* of them | `graph.service.ts:151-152`; `repository.controller.ts:140-161`; `server.ts:31` (bare `cors()`) | Once a second user exists this is a data leak. Add an ownership guard in the application layer (F.3) and make `repository` mandatory; restrict CORS to the known origins | UR-01/03/08; AR-01; Diagrams 1,2 |
| **E3** | 🟠 | **Private source fragments leave the server.** `sourceSnippet` is persisted and re-attached to nodes returned by `GET /api/graph` | `graph.service.ts:184-186`; `entity.extractor.ts:35-73` | Up to 700 chars of private implementation per function, readable unauthenticated, while the ZIP itself is deleted. The AI path needs it server-side only — stop serializing it to clients, or gate it behind ownership + plan | UR-07/08 privacy posture; AR-03 |
| **E4** | 🔴 | **Caches have no tenant dimension.** Report cache key is `repository:model:promptVersion:signature`; summary cache is `repository:model:promptVersion:nodeId`; the browser cache is `repository:nodeId` | `report.service.ts:225-226`; `function-summary.service.ts:75-76`; `api.ts:141` | Cross-user cache leakage the moment two users share a repository name (E1) or read the same graph. Add the owner (or UUID) to every cache key and to the invalidation prefix | UR-06/08/09; Diagrams 2,5 |
| **E5** | 🟠 | **Write path is N+1 with no batching, no `MERGE`, no constraints, no indexes.** One statement per node, two `MATCH` + one `CREATE` per edge, unindexed property lookups | `graph.service.ts:71-127`; verified absence of `CREATE CONSTRAINT/INDEX` in `backend/src` | Slow and fragile at scale (build-log evidence: ~65 s for a 53-node repository) and allows partial/duplicate writes. Batch with `UNWIND $nodes`, use `MERGE` on `(repository,id)`, add a uniqueness constraint and an index on `repository` | D-04; UR-03; Diagrams 1,7 |
| **E6** | 🟠 | **Long-running work executes inside one HTTP request.** No job, status, progress or resume; the whole repository is held in memory | `repository.controller.ts:51-134`; `analysis.service.ts` | Timeouts and proxy limits, no way to show "processing", no retry semantics, memory pressure on large repos. Target: create the run row, return `202 {analysisRunId}`, execute, update status — still in-process (no queue infrastructure) | UR-03/04; Diagrams 3,5 |
| **E7** | 🟠 | **The provider's `usage` payload is discarded, so nothing can be metered or costed.** The response interface has no `usage` field; only `choices[0].message.content` is read | `llm.client.ts:22-31`, `124-136` | UR-09 and AR-06 are unimplementable as written; any cost figure today would be fabricated. Capture `usage` when present, mark it unknown when absent, and keep estimated vs actual explicit | UR-09; AR-04/06; D-10; Diagram 9 |
| **E8** | 🟠 | **LLM configuration is a global singleton, so per-user credentials cannot be supported.** The key is read from `env.llm.key` inside the client rather than passed in | `env.ts:34-39`; `llm.client.ts:46,63-85` | BYOK (UR-08) needs a `complete(request, credentials)` seam; otherwise one user's requests bill to the platform key and every user shares one provider identity. Introduce a narrow provider interface here (a justified DIP case, not decoration) | UR-08/09; D-15; Diagrams 2,5,6,9 |
| **E9** | 🟡 | **Stateful caches are in-process `Map`s with no TTL, no eviction and no sharing** | `report.service.ts:195-196`; `function-summary.service.ts:24-25`; `api.ts:130` | Unbounded memory growth, cost lost on restart, and it silently breaks if the app is ever run as more than one process. Move to a persisted store (F.2 `analysis_reports`) with bounded entries, or an explicit TTL | UR-04/06; Diagrams 2,5 |
| **E10** | 🟡 | **Response-shaping business logic lives in the controller** (`categoryCounts` built in the handler; graph returned inline in the create response) | `repository.controller.ts:104-120` | Keeps entitlements/ownership logic out of the one place that will need it most; the 201 payload also duplicates the whole graph that `GET /api/graph` can serve. Move shaping into a service and consider returning counts + a run id | UR-03/06; Diagram 6 |
| **E11** | 🟡 | **Error surface leaks internals; no rate limiting; permissive CORS** | `server.ts:31`, `45-57` | `error.message` returned raw can expose paths or driver details; unauthenticated AI endpoints are a billing/DoS risk once BYOK/platform keys exist. Add an error taxonomy, redacted logging, and rate limits on AI + analyze routes | AR-03/D §admin security |
| **E12** | 🟡 | **Upload is written to disk before it is validated.** No Multer `fileFilter`; magic-byte check happens in the controller after the file exists | `repository.routes.ts:17-22`; `repository.controller.ts:70-80` | Any client can park up to 50 MB per request on the server before rejection; no per-user budget (E1/E4 again). Reject by MIME/extension at the middleware layer, keep magic bytes as the real check, and add per-user caps | UR-07; D-09 |
| **E13** | 🟠 | **Unresolvable relationships are silently omitted, and the provenance vocabulary has no `unresolved` value** | `models/graph.types.ts:51-54` (derived/resolved/name-match); `relationship.extractor.ts` omission path | Directly contradicts the approved proposal ("explicitly marked as unresolved rather than guessed") and makes the map's completeness unmeasurable — which also blocks any accuracy evaluation (WBS 3.11). Add an `unresolved` marker/count before the change-impact module depends on traversal completeness | Proposal M1; master-doc W4; Diagrams 5,7 |
| **E14** | 🟡 | **Type/API drift.** `Variable` is declared and allow-listed but never emitted; the frontend's `AnalyzeResponse` omits `categoryCounts` the backend sends | `graph.types.ts:1-8` + `graph.service.ts:26`; `api.ts:5-11` vs `repository.controller.ts:113-120` | Dead vocabulary invites a reviewer to ask why a node type exists; the client type is inaccurate about its own payload. Either emit or remove; align the client type | Diagrams 6,7 |
| **E15** | 🟡 | **No CI, no coverage gate, no application container.** `docker-compose.yml` defines only Neo4j | repository search: no workflow file, no Dockerfile; `docker-compose.yml:1-14` | WBS 3.1's "CI environment" claim stays false; regressions in a 151-test suite depend on someone remembering to run it. Blocks any honest deployment diagram | D-13; WBS 3.1/3.12; Diagram 10 |
| **E16** | 🟡 | **Filesystem paths resolve from the current working directory** (`path.resolve("uploads")`), and the compose file hardcodes a dev password | `env.ts:22-27`; `server.ts:24-27`; `docker-compose.yml:9` | Running the API from another cwd silently changes where uploads land — confusing for quota/retention work. Dev credential is acceptable locally but must not leak into a deployment story | D-09; Diagram 10 |
| **E17** | 🟡 | **`fetchFunctionContext` reduces graph context to a set of names** | `graph.service.ts:286-316` | Two distinct callees (or callers) with the same name collapse into one prompt entry, so the "grounded in the graph" claim is slightly weaker than it looks; ambiguity also hurts a future change-impact traversal. Return ids + names | UR-05/D-06; Diagram 5 |

## Part 3 — Things deliberately **not** recommended

Stated so nobody reads the review as a wish list:

1. **No microservices.** One pipeline, one process, one team; nothing measured justifies a
   split. Modules are namespaces (§D.1).
2. **No queue broker, no cache server, no warehouse** at FYP scale. A run-status column and
   query-time aggregation do the job (D-04, D-12).
3. **No new interface everywhere DIP was mentioned.** Only the three genuinely variable
   seams: LLM provider (E8), storage location (D-09), payment boundary (D-08).
4. **No table per screen** — the user-visible work log is a derived view (§B.3, F.2.1).
5. **No rewrite of the pipeline.** Its fault tolerance, provenance, path separation and
   best-effort persistence are the most valuable thing in the repository and are preserved
   as-is (§C.3, D.6).
6. **No silent refactoring.** Findings E1–E17 are reported, not applied; each fix belongs in
   a build log entry with its own verification.
