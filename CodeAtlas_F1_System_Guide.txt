 1. WHAT CODEATLAS F1 DOES (SCOPE)
================================================================================

CodeAtlas turns a JavaScript / TypeScript repository into an interactive
knowledge graph so a developer can understand an unfamiliar codebase quickly.

The F1 pipeline (the only scope implemented so far) is:

   Repository ZIP
      -> Repository Scanner      (find source files)
      -> AST Parser              (Babel)
      -> Entity Extraction       (nodes)
      -> Relationship Extraction (edges)
      -> Graph Builder           (validate + assemble)
      -> Neo4j                   (persistence)
      -> REST API                (Express)
      -> React + D3              (interactive graph)

F1 node types      : Repository, Directory, File, Class, Function, Method
                     (Variables may exist internally, not shown by default)
F1 relationship    : CONTAINS, IMPORTS, CALLS, EXTENDS
F1 input           : a .zip archive of a JS/TS project
F1 output          : an interactive force-directed graph in the browser, with
                     zoom / pan / drag / click and a node-details panel.

NOT in F1 (deliberately out of scope for now): LLM/AI explanations, RAG,
change-impact analysis, technical-debt or vulnerability analysis, auth,
billing, guided tours, project export, .rar/.7z input, Git URL input.

 2. HOW TO RUN IT
================================================================================

Prerequisites
  - Node.js 18+            (node -v)
  - Neo4j 5.x running       (Neo4j Desktop instance, or Aura)
  - Dependencies installed  (npm install inside backend/ and frontend/)

Two terminals are required (there is NO package.json at the project root):

  Terminal 1 - backend (API):
      cd /d D:\University\FYP\implementation\codeatlas-prototype\backend
      npm install        (first time only)
      npm run dev        ->  http://localhost:5000

  Terminal 2 - frontend (dashboard):
      cd /d D:\University\FYP\implementation\codeatlas-prototype\frontend
      npm install        (first time only)
      npm run dev        ->  http://localhost:5173

Then open http://localhost:5173, choose a .zip, click "Analyze repository".

Config file: backend/.env
      NEO4J_URI=neo4j://127.0.0.1:7687
      NEO4J_USERNAME=neo4j
      NEO4J_PASSWORD=codeatlas123
      NEO4J_DATABASE=neo4j
      PORT=5000

  IMPORTANT: use 127.0.0.1 (not "localhost"). "localhost" can resolve to the
  IPv6 address ::1, while Neo4j listens on IPv4 127.0.0.1, which causes a
  connection-refused error.

Health check:  http://localhost:5000/api/health  ->  {"status":"ok","neo4j":true}

 3. HIGH-LEVEL ARCHITECTURE
================================================================================

  BROWSER (React + D3, http://localhost:5173)
     |
     |  HTTP (JSON + multipart). Vite dev server proxies "/api" -> :5000
     v
  BACKEND (Express 5 + TypeScript, http://localhost:5000)
     |
     +-- routes/         -> controllers/        (HTTP layer)
     |                        |
     |                        +--> ingestion.service   (ZIP -> files on disk)
     |                        +--> parser.service      (orchestrates analysis)
     |                               |
     |                               +--> analysis.service   (the pipeline)
     |                               |       |
     |                               |       +--> repository.service (scan)
     |                               |       +--> parser/*           (Babel/TS)
     |                               |
     |                               +--> graph.service        (Neo4j read/write)
     |
     +-- config/env        (loads .env)
     +-- database/neo4j    (driver)

  NEO4J (bolt://127.0.0.1:7687)  - nodes labeled :Entity:<Type>, edges typed

Design principles:
  - The BACKEND builds the graph. The FRONTEND only renders what the API
    returns (the frontend never constructs graph semantics).
  - Physical filesystem paths are kept separate from the repository-relative
    paths used in graph IDs. Machine paths are never exposed in the graph.
  - One bad file must never abort the whole analysis (fault tolerance).
  - Persistence is best-effort: if Neo4j is down the graph is still returned.

 5B. BACKEND - CONFIGURATION, DATABASE, MODELS, UTILITIES
--------------------------------------------------------------------------------

backend/package.json
  Dependencies:
    @babel/parser, @babel/traverse   -> JavaScript/TypeScript AST parsing
    express, cors, multer            -> HTTP server, CORS, file uploads
    neo4j-driver                     -> Neo4j Bolt driver
    unzipper                         -> ZIP extraction
    dotenv                           -> .env loading
  Dev dependencies:
    vitest, supertest                -> automated tests (runner + HTTP)
    typescript, ts-node-dev          -> type-checking, dev server
  Scripts:
    dev        = ts-node-dev --respawn --transpile-only src/server.ts
    build      = tsc -p tsconfig.build.json   (excludes tests/fixtures)
    start      = node dist/server.js
    analyze    = ts-node src/test-analysis.ts
    typecheck  = tsc --noEmit
    test       = vitest run
    test:watch = vitest
  (dev-broken script from before: the original only had a placeholder "test"
   script and no way to start the server.)

backend/tsconfig.build.json
  Build-only TypeScript config that extends tsconfig.json and EXCLUDES
  src/**/*.test.ts and src/test-fixtures/**, so `npm run build` never emits
  test artifacts into dist/. `npm run typecheck` uses tsconfig.json and so
  still type-checks the tests.

backend/vitest.config.ts
  Vitest configuration: node environment, includes src/**/*.test.ts, and
  excludes node_modules, dist, extracted and src/test-fixtures/** (the
  fixtures are sample code, not specs).

backend/tsconfig.json
  Strict TypeScript, CommonJS output to dist/. "include": ["src"] so ALL
  source is type-checked (previously only a subset was included, which hid
  real compile errors). Also sets "ts-node": { "files": true } so ts-node
  loads ambient .d.ts files (needed for the "unzipper" declaration).

backend/src/config/env.ts
  Loads environment variables ONCE and exposes a typed "env" object.
  - Uses dotenv with an explicit path (../../.env) so it works regardless of
    the current working directory.
  - Provides defaults for neo4j uri/username/password/database, PORT (5000),
    uploadsDir and extractedDir (absolute paths).
  This is the single source of configuration truth.

backend/src/database/neo4j.ts
  Creates and exports a single Neo4j driver (singleton) plus the database name.
  - Reads config from env.ts (NOT directly from process.env).
  - Sets disableLosslessIntegers: true so integer values (e.g. line numbers)
    are returned as plain JS numbers (clean JSON) instead of Neo4j Integer
    objects.

backend/src/models/graph.types.ts
  The shared contract used by the whole backend:
    EntityType        = Repository | Directory | File | Class | Function |
                        Method | Variable
    RelationshipType  = CONTAINS | IMPORTS | CALLS | EXTENDS
    GraphNode         { id, type, name, filePath, startLine, endLine,
                        category?, inDefaultScope? }
    GraphRelationship { source, target, type, evidence? }
    RelationshipEvidence { filePath?, line?, resolution }
    ResolutionMethod  = derived | resolved | name-match
    FileCategory      = source | test | config | fixture | generated |
                        declaration
    GraphData         { nodes[], relationships[] }
  "evidence" records HOW an edge was found (provenance): "derived" for
  structural ownership computed from paths, "resolved" for a concrete target
  resolved via an import path or the TS symbol resolver, and "name-match" for
  EXTENDS (matched by class name). It is optional so the type stays
  backward-compatible; the frontend mirrors these in its own types.ts.

backend/src/utils/ignore.utils.ts
  Defines IGNORED_DIRECTORIES (node_modules, .git, dist, build, coverage,
  .next, out, vendor) and isIgnoredDirectory(name). Central place for scan
  ignore rules (previously hard-coded inside repository.service).

backend/src/utils/file.utils.ts
  Small, focused filesystem helpers used by ingestion and the controller:
    ensureDirectory(path)        mkdir -p
    isPathInside(parent, child)  true only if child is within parent
                                 (used to reject "zip-slip" archive entries)
    toPosixPath(value)           backslashes -> forward slashes
    removeDirectoryIfExists(p)   recursive delete
    removeFileIfExists(p)        delete one file (cleanup of uploaded ZIPs)
    isZipArchive(path)           reads the first 2 bytes and checks the ZIP
                                 magic number "PK" (rejects RAR/7z/bogus)

backend/src/types/unzipper.d.ts
  The "unzipper" package ships no TypeScript types. This ambient declaration
  describes the minimal API we use (Open.file(...).files, each entry's path,
  type and stream()) so the project stays strictly typed.

 5C. BACKEND - THE PARSER PACKAGE (AST PIPELINE)
--------------------------------------------------------------------------------

backend/src/parser/ast.parser.ts
  parseFile(filePath): reads the file and parses it with Babel
  (@babel/parser) into an AST.
  - Chooses plugins by file EXTENSION:
      .ts        -> ["typescript"]
      .tsx       -> ["typescript","jsx"]
      .jsx       -> ["jsx"]
      .js/.other -> []  (plain JS)
    (The "jsx" plugin is intentionally NOT enabled for .ts so that
     angle-bracket type assertions still parse.)
  - sourceType "module", ranges enabled.

backend/src/parser/entity.extractor.ts
  extractEntities(ast, filePath): walks the AST and emits NODES.
  - Always emits one "File" node (id file:<relativePath>).
  - ClassDeclaration   -> Class node   (id class:<path>:<ClassName>)
  - FunctionDeclaration-> Function node(id function:<path>:<Name>)
  - VariableDeclarator -> Function node(id function:<path>:<Name>) WHEN the
    initializer is a function value (`const x = () => {}` or
    `const x = function () {}`). This represents modern JS/TS codebases where a
    large share of functions are declared as arrow/const functions.
  - ClassMethod        -> Method node  (id method:<path>:<ClassName>:<Name>)
    The method id is QUALIFIED with its enclosing class name, so two classes
    in the same file can share a method name without colliding.
  Every node records type, name, filePath and start/end line.

backend/src/parser/relationship.extractor.ts
  extractRelationships(ast, context, entities, symbolResolver): walks the AST
  and emits EDGES. "context" carries three paths:
      filePath          repository-relative (used for IDs)
      absoluteFilePath  physical path (used for import resolution)
      repositoryRoot    repo root (used to make resolved paths relative)
  Produces (each edge tagged with provenance via an "evidence" object):
    CONTAINS : file -> class, class -> method, file -> function
               (including const/arrow functions)          [derived]
    IMPORTS  : file -> resolved local file   (via module-resolver) [resolved]
    EXTENDS  : class -> superclass           (best-effort, by name) [name-match]
    CALLS    : function/method -> resolved callee (via symbol-resolver) [resolved]
  Helpers:
    getMethodKey(node)      extracts a method's name (Identifier or string key)
    findClassEntityId(name) matches a superclass name to a Class entity
                            (same file first, then anywhere; if not found the
                             EXTENDS edge is simply omitted)
    isFunctionValue(node)   true for `() => {}` / `function () {}` initializers,
                            mirroring entity.extractor so CONTAINS and CALLS
                            attribute to the same Function entity
  CALLS logic: for each CallExpression it finds the enclosing function/method
  (the "caller" - a FunctionDeclaration, a ClassMethod, or a const/arrow
  function), then asks the symbol resolver to resolve the call target at the
  call's start offset; the edge is only emitted if the target node exists.

backend/src/parser/module-resolver.ts
  resolveModule(currentAbsoluteFilePath, importPath, repositoryRoot): maps a
  local import to a repository-relative path, or null.
  - Only relative imports ("./", "../") are resolved; packages are ignored.
  - Tries the exact path plus .ts/.tsx/.js/.jsx and /index.* variants.
  - Handles ESM-style ".js" imports that actually point at ".ts" sources
    (e.g. import "./constants.js" -> constants.ts), which is common in modern
    TypeScript.

backend/src/parser/symbol.resolver.ts
  createSymbolResolver(repositoryRoot, absoluteSourceFiles): builds a
  TypeScript PROGRAM (ts.createProgram) over all source files and returns a
  resolver exposing resolveCallFromLocation(filePath, position).
  - getSourceFile(path)   finds the matching ts.SourceFile (case-insensitive,
                          normalized separators)
  - findCallExpression()  finds the CallExpression at an offset; it keeps
                          descending so the INNERMOST call wins (this
                          correctly resolves nested calls like outer(inner()))
  - resolveCallFromLocation(): gets the symbol at the call's callee, follows
                          import aliases (getAliasedSymbol), then converts the
                          declaration into a CodeAtlas id.
  - getCodeAtlasId():     maps a resolved declaration to
                            function:<relativePath>:<Name>
                            method:<relativePath>:<ClassName>:<Name>
                          using paths relative to the repository root.

backend/src/parser/graph.builder.ts
  buildGraph(entities, relationships, repositoryName): the final assembly and
  validation step. It:
  - Creates the Repository node (id repository:<name>).
  - Deduplicates nodes by id (Map).
  - Derives Directory nodes from each File node's path and adds CONTAINS
    edges repository -> top-level dir/file, dir -> child dir/file. These
    derived edges are tagged evidence.resolution = "derived".
  - Filters out relationships whose source or target node does not exist
    (dangling edges) and self-loops.
  - Deduplicates relationships by source|type|target (evidence carried on the
    first occurrence is preserved).
  Returns a clean GraphData { nodes, relationships }.


--------------------------------------------------------------------------------
 5D. BACKEND - THE SERVICE LAYER
--------------------------------------------------------------------------------

backend/src/services/repository.service.ts
  findSourceFiles(repositoryPath): recursively scans a directory and returns
  the list of source files (extensions .ts .tsx .js .jsx) as repository-
  relative paths with forward slashes. Skips ignored directories via
  ignore.utils. This is the "Repository Scanner".

backend/src/services/analysis.service.ts
  analyzeRepository(repositoryPath, repositoryName?): THE PIPELINE
  ORCHESTRATOR. Phases:
    PHASE 1/2  For each source file: parseFile(absolutePath) then
               extractEntities(ast, relativePath). Files are tracked with a
               RelationshipContext so physical and relative paths stay
               separate. A file that fails to parse is logged and SKIPPED
               (one bad file never kills the run).
    PHASE 2    Build the TypeScript program over all parsed files via
               createSymbolResolver(repositoryRoot, absoluteFiles).
    PHASE 3    For each parsed file: extractRelationships(ast, context,
               entities, symbolResolver). Per-file errors are caught + logged.
    PHASE 4    buildGraph(entities, relationships, repositoryName).
  Returns GraphData. The repository name is used for the Repository node and
  the persistence scope (defaults to the folder name if not provided).

backend/src/services/scope.service.ts
  annotateScope(graph): relevance pass run after buildGraph. It sets
  File.category (via classify.utils) and inDefaultScope on every node. A file
  is in scope when it is "source" OR is imported (directly/transitively) by a
  source file (reachability keeps a relevant module outside the main source
  directory). Directories inherit scope from their in-scope files; the
  Repository is in scope when any file is. This is a VISUALISATION concern -
  no node or relationship is ever removed.

backend/src/utils/classify.utils.ts
  classifyFile(relativePath, fileName) -> FileCategory (source/test/config/
  fixture/generated/declaration), using combined path-segment AND filename
  signals rather than folder names alone.

backend/src/services/ingestion.service.ts
  ZIP ingestion ("Repository Scanner" input stage):
    sanitizeName(name)        turns the upload name into a safe folder name
    resolveRepositoryRoot(dir) if the archive has a single top-level folder,
                              descend into it (the common "project folder"
                              layout)
    extractZip(zipPath, name) opens the ZIP with unzipper and writes each
                              entry under extracted/<name>-<timestamp>/. Each
                              entry is validated with isPathInside() so a
                              malicious "../../" entry (zip-slip) is skipped.
  Returns { repositoryName, repositoryPath }.

backend/src/services/parser.service.ts
  analyzeAndStore(repositoryPath, repositoryName):
    - runs analyzeRepository(...)
    - tries saveGraph(graph, repositoryName) to persist to Neo4j
    - if persistence fails (Neo4j down) it logs a warning and continues,
      returning { graph, persisted: false }
  Returns { graph, persisted }. This is what makes the demo resilient: the
  graph is always returned even without a database.

backend/src/services/graph.service.ts
  The Neo4j persistence + retrieval layer.
    ENTITY_LABELS / RELATIONSHIP_TYPES : allow-lists. Only known node types and
        relationship types are written, so graph data can never inject Cypher
        through a label.
    entityLabels(type)      -> ":Entity:<Type>" (or ":Entity")
    relationshipType(type)  -> the relationship type name (or "RELATIONSHIP")
    saveGraph(graph, name)  - deletes only THIS repository's nodes
                              (MATCH (n:Entity {repository:$repository}) DETACH
                              DELETE n), then CREATes each node with labels
                              :Entity:<Type> plus properties (id, type, name,
                              filePath, startLine, endLine, repository) and
                              each relationship, storing the relationship's
                              provenance as properties (line, filePath,
                              resolution). Re-analysing the same repository is
                              idempotent and does NOT touch other repositories.
    fetchGraph(repository?) reads nodes + relationships back out (optionally
                            scoped to one repository) and rebuilds the
                            "evidence" object when a resolution property is
                            present.
    listRepositories()      returns the names of repositories with a graph.
    verifyConnection()      used by the health endpoint; returns true/false.

 5E. BACKEND - CONTROLLERS, ROUTES, SERVER
--------------------------------------------------------------------------------

backend/src/controllers/repository.controller.ts
  The HTTP handlers (thin: validation + service calls only):
    health()                 -> { status, neo4j }

backend/src/routes/repository.routes.ts
  Defines the router and the multer upload middleware (disk storage into
  backend/uploads, 50 MB limit, field name "file"). Routes:
    GET  /health
    GET  /repositories
    GET  /graph
    POST /repositories/analyze   (multipart "file")

backend/src/server.ts
  The Express application entry point:
    - enable CORS and JSON body parsing
    - mount the router under /api
    - a 404 handler (JSON)
    - a central error handler (logs and returns JSON 500)
    - EXPORTS the app; it only calls listen() (env.port, default 5000) when the
      file is run directly (require.main === module), so tests can import the
      app with Supertest without opening a port.

================================================================================
 6. END-TO-END EXECUTION FLOW (one upload, step by step)
================================================================================

  1. User picks a .zip in UploadPanel and clicks "Analyze repository".
  2. api.analyzeArchive(file) sends POST /api/repositories/analyze as
     multipart/form-data (field "file").
  3. Vite dev server proxies /api/* to the backend on port 5000.
  4. server.ts (Express) -> cors, json -> routes/repository.routes.ts.
     The multer middleware streams the upload into backend/uploads/.
  5. controller.analyzeRepositoryUpload():
       - rejects non-ZIP (extension and "PK" magic bytes) with HTTP 400;
       - calls ingestion.extractZip() -> files land under
         backend/extracted/<name>-<timestamp>/ (zip-slip entries skipped),
         and the repository root is resolved.
  6. parser.service.analyzeAndStore(repositoryPath, repositoryName):
       a. analysis.service.analyzeRepository():
            - repository.service.findSourceFiles() lists .ts/.tsx/.js/.jsx
            - for each file: ast.parser.parseFile() (Babel) ->
              entity.extractor.extractEntities()  [File/Class/Function/Method]
            - symbol.resolver.createSymbolResolver() builds the TS program
            - relationship.extractor.extractRelationships() per file
              [CONTAINS, IMPORTS via module-resolver, EXTENDS, CALLS via the
               TS symbol resolver]
            - graph.builder.buildGraph() [add Repository+Directory nodes,
              dedupe nodes, drop dangling/duplicate edges]
       b. graph.service.saveGraph(graph, name): writes to Neo4j
          (scoped delete for this repository, then nodes and relationships).
          If Neo4j is unreachable this is caught; persisted=false.
  7. Controller responds 201 with { repository, persisted, nodeCount,
     relationshipCount, graph } and deletes the temp upload file.
  8. App.tsx stores the graph and shows the status line; GraphView runs the
     force simulation and renders the interactive graph; clicking a node
     populates DetailsPanel.

  Reload path:
     "Load stored graph" -> api.loadGraph() -> GET /api/graph ->
     controller.getGraph() -> graph.service.fetchGraph() -> Neo4j ->
     the same graph is rendered again.


================================================================================
 7. GRAPH DATA MODEL
================================================================================

Node identity (globally unique WITHIN one analysed repository, and derived
from REPOSITORY-RELATIVE paths so machine paths never leak):

  Repository   repository:<name>
  Directory    directory:<relativeDirPath>            e.g. directory:core
  File         file:<relativeFilePath>               e.g. file:core/Ky.ts
  Class        class:<relativeFilePath>:<ClassName>
  Function     function:<relativeFilePath>:<Name>
  Method       method:<relativeFilePath>:<ClassName>:<Name>

  Example (from a real repo):
      function:utils/normalize.ts:normalizeRequest
      method:core/Ky.ts:Ky:constructor

Relationship types:
  CONTAINS : structural ownership (repository/dir/file containing children)
  IMPORTS  : a file imports a local file
  CALLS    : a function/method calls another function/method
  EXTENDS  : a class extends another class

Relationship provenance (evidence):
  Each edge may carry { filePath?, line?, resolution } where resolution is
  "derived" (computed from paths/ownership), "resolved" (concrete target from an
  import path or the TS symbol resolver) or "name-match" (EXTENDS, matched by
  class name). In Neo4j these are stored as relationship properties.

Each node also carries: name, filePath, startLine, endLine.
In Neo4j every node is labeled :Entity and also with its specific type
(e.g. :Entity:Function), and stores a "repository" property used to scope
queries and deletions.


================================================================================
 8. REST API REFERENCE
================================================================================

  GET  /api/health
       -> { "status": "ok", "neo4j": true|false }

  POST /api/repositories/analyze      (multipart/form-data, field "file")
       -> 201 { repository, persisted, nodeCount, relationshipCount, graph }
       -> 400 { error } for a missing / non-ZIP / unreadable archive

  GET  /api/graph                     -> { nodes: [...], relationships: [...] }
  GET  /api/graph?repository=<name>   -> scoped to one repository
  GET  /api/repositories              -> { repositories: [ "name", ... ] }

  graph = { "nodes": [ {id,type,name,filePath,startLine,endLine}, ... ],
            "relationships": [ {source,target,type,
                                evidence:{filePath,line,resolution}}, ... ] }


================================================================================
 9. ERROR HANDLING & FAULT TOLERANCE
================================================================================

  - A single file that fails to PARSE is logged and skipped; the rest of the
    repository is still analysed (analysis.service per-file try/catch).
  - Relationship extraction for a file is wrapped in its own try/catch.
  - Unresolved imports and unresolved calls are simply omitted (never crash).
  - Duplicate node ids and duplicate/dangling edges are removed in
    graph.builder.
  - Non-ZIP uploads are rejected up front with a clear 400 message
    (previously produced a cryptic "FILE_ENDED" from the ZIP parser).
  - If Neo4j is unavailable, analyze still succeeds and returns the graph with
    persisted=false; /api/health reports neo4j:false.
  - Central Express error handler returns JSON for unexpected errors.

12. KNOWN LIMITATIONS & FUTURE WORK (F2+)
================================================================================

  - Input formats: ZIP only (no RAR/7z, no Git URL yet).
  - Languages: JS/TS only (Babel + TypeScript).
  - Symbol resolution is best-effort: dynamic imports, re-exports, aliases,
    overloaded/ambiguous names and external packages may be omitted (by
    design - F1 prioritises a working graph over perfect accuracy).
  - EXTENDS is matched by class NAME (same file first), so a same-named class
    elsewhere could theoretically be chosen.
  - Calls INTO const/arrow functions are not resolved: symbol.resolver maps only
    function/method declaration nodes, so a call whose target is a `const x =
    () => {}` is omitted. Const/arrow functions ARE emitted as entities and ARE
    recognised as CALLS callers (calls made from within them are attributed
    correctly).
  - Calls inside object-literal methods are not attributed to a named caller.
  - File classification is heuristic (path + filename signals); unusual layouts
    may be mis-categorised (visible via the Application <-> Full toggle).
  - Derived (Repository/Directory) CONTAINS edges carry a resolution but no
    filePath/line, because they are computed from paths rather than a source
    location.
  - No coverage reporting or CI pipeline yet; the test suites are run manually.
  - No authentication, no multi-user isolation (repository scoping exists but
    there is no user model).
  - The graph is re-analysed in full each time (no incremental analysis).
  - Large graphs may need level-of-detail / clustering for readability
    (currently labels are thinned above 80 nodes).

  Intended later features (explicitly NOT in F1): LLM/AI explanations, RAG,
  guided tours, change-impact analysis, technical-debt and vulnerability
  analysis, project export, billing/auth, Git-URL ingestion, and improved
  semantic precision.

13. GLOSSARY
================================================================================

  AST          Abstract Syntax Tree - the parsed structure of source code.
  Babel        Library used to parse JS/TS into an AST.
  Entity / Node   A code element (Repository/Directory/File/Class/Function/
                  Method) represented as a graph node.
  Relationship / Edge  A typed connection between two nodes
                  (CONTAINS/IMPORTS/CALLS/EXTENDS).
  Cypher       Neo4j's query language.
  Bolt         Neo4j's binary protocol (port 7687).
  zip-slip     A malicious archive path ("../") that escapes the target
               directory; rejected via isPathInside().
  Repository-relative path  A path relative to the analysed project's root
               (used in graph IDs). Distinct from the physical filesystem path.
